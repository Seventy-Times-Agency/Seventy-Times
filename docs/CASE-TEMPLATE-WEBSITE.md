# Шаблон кейса — САЙТЫ

Дополняет `CASE-TEMPLATE.md`. Здесь только то, что специфично для сайтов.

**Чем website-кейс отличается от рекламного.**
В рекламе доказательство — цифры из кабинета. В сайте главное доказательство —
**сам сайт, который можно открыть и потрогать**, плюс объяснение решений.

Портфолио: «вот скриншот, красиво».
Кейс: «вот скриншот, вот зачем это так сделано, вот что было вместо этого».

Каждый кейс должен рассказывать историю: **зачем сайт был нужен → что мешало →
что мы решили → что получилось**.

## БЛОК 1. Запрос — с чего началось

Это открывающая история. Три вопроса:

| Поле | | |
|---|---|---|
| С чем пришёл клиент | [ОБЯЗАТЕЛЬНО] | своими словами, 1–2 предложения |
| Что было до | [ОБЯЗАТЕЛЬНО] | см. три варианта ниже |
| Почему именно сейчас | [СИЛЬНО] | что подтолкнуло: запуск, сезон, потеря заявок |

**Три варианта «до»:**

1. **Был старый сайт** — скриншоты обязательны, если сайт ещё жив или есть
   в веб-архиве
2. **Сайта не было, были соцсети или сарафан** — описываем, как бизнес получал
   клиентов и где это ломалось
3. **Бизнес новый, не было ничего** — описываем, что нужно было построить с нуля
   и под какую задачу

Третий вариант — не слабость. «Запускали с нуля под конкретный рынок» —
нормальная история, если дальше объяснены решения.

## БЛОК 4. Решения — ядро кейса

**Самый важный блок.** 4–8 решений. Для каждого — четыре поля:

```
скриншот:   /cases/<slug>/01-hero.webp
что это:    первый экран с телефоном в шапке
зачем так:  у клиента 80% трафика с мобильных, звонок — главное действие,
            поэтому номер закреплён в шапке и кликабелен
было:       телефон стоял в подвале, с мобильного не находился
```

Поле **«зачем так»** обязательно. Без него это портфолио, а не кейс.
Поле «было» заполняется, если старый сайт существовал.

Что показывать: первый экран, ключевую страницу услуги, форму заявки,
мобильную версию, каталог, оформление заказа — в зависимости от проекта.

Не показывать по восемь красивых макетов без объяснений.

## БЛОК 7. Результат

Здесь у сайтов есть преимущество: **часть метрик мы измеряем сами**,
без доступа к аналитике клиента. Это честные, публично проверяемые цифры.

**Измеряем сами** [СИЛЬНО] — работает всегда:

| Показатель | Было | Стало | Источник |
|---|---|---|---|
| PageSpeed, мобильный | 34 | 96 | PageSpeed Insights |
| LCP | 6.1 с | 1.2 с | PageSpeed Insights |
| Мобильная адаптация | нет | да | Mobile-Friendly Test |
| Страниц в индексе | 1 | 58 | sitemap, Search Console |
| Языков | 1 | 3 | сайт |

Старый сайт для замера берём из веб-архива, если он уже заменён.

**Даёт клиент** [ОПЦИЯ] — если делится аналитикой:
конверсия, заявки, отказы, время на сайте, выручка.
Формат тот же: показатель, было, стало, срок, источник.

**Если клиент не даёт ничего** — кейс всё равно состоятелен: есть живая ссылка,
есть решения с объяснениями, есть самостоятельно измеренная техника.
Так и пишем, без выдуманных «+250% конверсии».

## Порог публикации для website-кейса

1. Живая ссылка на сайт
2. Запрос — с чем пришёл клиент
3. Главное препятствие
4. Задача сайта и одно целевое действие
5. **Минимум четыре решения с заполненным «зачем так»**
6. Замеры, которые мы сделали сами (PageSpeed как минимум)

Скриншоты «до» и цифры клиента — усиливают, но не блокируют.

## Порядок экранов на странице кейса

```
01  Результат      — что это за сайт, ссылка, крупный скриншот
02  Запрос         — с чем пришёл клиент, что было до
03  Что мешало     — главное препятствие
04  Задача         — что сайт должен делать
05  Решения        — 4–8 блоков «скриншот + зачем так»
06  До / После     — если есть материалы
07  Техника        — стек и замеры
08  Слова клиента  — если есть настоящие
09  Итог и призыв
```

Мобильная версия — та же последовательность, но решения идут по одному
на экран, а не сеткой.
